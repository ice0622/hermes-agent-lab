# 健康管理エージェント 仕様

作成 2026-08-24 / `/grilling` ラウンド1〜3の確定事項

## 動機

彫刻のような肉体が欲しい。筋トレは1年続いているが記録が紙で見にくく、食事管理まで手が回らない。
面倒なのは記録そのものではなく、**何をどれだけ買えばいいかを毎回考えること**。

## 対象者の実測値

| | 値 |
|---|---|
| 生年月日 / 年齢 | 2001-06-22 / 25歳 |
| 身長 / 体重 | 178cm / 64kg（BMI 20.2） |
| 筋トレ | 継続11ヶ月・**86セッション**（実測。`docs/training-history.md`） |
| 頻度 | **週1.2〜2.3回**（自己申告の「週3〜4」より少ない。実測で判明） |
| 現在の摂取 | 未測定（消費を下回っている自覚あり） |

### 1年分の実測から判明したこと

紙の記録（2025-09-20〜2026-08-19、86セッション）を書き起こして集計した結果。
**この仕様書の前提を、本人のデータが裏付けた。**

1. **増量を目標にしているが、実際は減量している。**
   2025年12月30日にピーク 67.5kg → 直近 64.0kg で **−3.5kg**。
   月平均では 2026年1月 66.5kg → 2026年6-8月 64.3kg で **−2.2kg**
2. **筋力が2025年12月から8ヶ月停滞。** ベンチプレス推定1RM は
   38.0kg（2025-09）→ 46.7kg（2025-12）と最初の3ヶ月で +8.7kg 伸びたあと、
   44〜49kg で横ばい。体重が落ちている期間に筋力が伸びないのは自然な帰結
3. **頻度が2026年2月以降に週1.2〜1.6回まで低下。** 停滞のもう一つの要因
4. **2026年7月末から有酸素（トレッドミル 傾斜9% / 30分）を追加している。**
   増量目標と方向が逆。消費を増やしている
5. 分割は実質 **Push / Pull / Legs** で固まっているが、**曜日は固定されていない**

→ 1〜3 は同じ原因（摂取不足）で説明がつく。**この仕組みが最初に解くべき問題は、
体重を戻すことである**ことが実測で確定した。4 はフェーズ1の期間中は止める判断もあり得る。

## 成功の定義

**週平均体重が +200〜300g で推移し続けている。**

副次: 毎日「あと何 kcal・タンパク質何 g 足りないか」と「それを埋める具体的な商品名」が
手元にある状態。紙の記録を捨てられている。

## 目標値（初期仮説）

Mifflin-St Jeor + 活動係数1.55。**この数字は仮説であり、実測で補正する**（下記の制御ループ）。

| | 値 | 根拠 |
|---|---|---|
| 基礎代謝 | 1,633 kcal | 10×64 + 6.25×178 − 5×25 + 5 |
| 消費カロリー(TDEE) | **2,530 kcal** | ×1.55 |
| 目標摂取 | **2,830 kcal** | TDEE +300（リーンバルク） |
| タンパク質 | **130 g** | 2.0 g/kg |
| 脂質 | 60 g | 0.9 g/kg |
| 炭水化物 | 440 g | 残り |

## 制御ループ（システムの心臓部）

TDEE の推定式には ±10% の誤差がある。だから目標値は固定せず、**体重の実測で毎週補正する**。

```
毎週日曜: 直近7日の体重平均 と 前週平均 を比較
  +300g 超    → 目標 −150 kcal（増えすぎ。脂肪が乗る）
  +200〜300g  → 維持（正常）
  +100g 未満  → 目標 +200 kcal
  減少        → 目標 +300 kcal
  → targets テーブルに追記（いつ・なぜ変えたかを残す）
```

**この判定に LLM は不要。** SQL と条件分岐だけ。システムで最も価値のある部分が、最も安い。

## 決定

### アーキテクチャ

- **SQLite ファイル1個（`~/health/health.db`）を唯一の真実とする。** API は作らない
- ダッシュボードは **静的 HTML 生成**（`dashboard.html` を書き出してブラウザで開く）。
  常駐プロセスなし。グラフは SVG を直接埋め込み、JS ライブラリも CDN も使わない
- 配色は白黒モノクロ。UI とインタラクションはフェーズ3
- Upstash / Vercel Postgres / Neon は**使わない**。「向こう側」がまだ存在しないため。
  将来クラウドに出す場合は Turso / libSQL（SQLite 互換）へ移行できる

### 入力

- **フェーズ1は CLI のみ。** Telegram は作らない（入力経路を増やすと記録形式が散らばる）
- ジムでは紙を継続し、帰宅後に CLI で一括入力。**紙を捨てるのは CLI 入力が3週間続いた後**
- 食事は品目単位で保存するが、入力は1行。
  `m サラダチキン, おにぎり*2, 味噌汁` → パーサーがカンマで分割して3行に展開
- 筋トレは略号 + セット。`bp 60 8,8,7` → 3行に展開
- 体重は数値1つ。`w 64.2`

### 記録の粒度

- 食事は**品目単位**（タンパク質の供給源を後から分析できる必要がある）
- 筋トレは**セット単位**（1RM推定・総挙上重量・漸進性過負荷の追跡のため）
- 体組成は1日1件

### 通知

- **原則は受動。** 記録は自分で打つ
- **例外は1本だけ: 18時の不足通知。** 「あと 900kcal、P 45g 足りない」
  → その日のうちに行動を変えられる唯一のタイミング
- 他の通知は作らない（無視される習慣がつくとチャンネル全体が信用を失う）

### 食品データ

- **自作の `foods` マスタ。外部 API は使わない**
- 初期30品を手打ち（実際にコンビニで買うものだけ）
- 未知の品が出たときだけ Sonnet 5 に栄養価を聞いて追記 → 二度目以降は $0
- 素材（鶏むね・米・卵など）は文科省 食品成分データベースから取り込む

### モデル

| 用途 | 手段 | 単価 |
|---|---|---|
| 筋トレ・体重の記録 | **正規表現パーサー（LLM 不使用）** | $0 |
| 既知食品の記録 | マスタ参照（LLM 不使用） | $0 |
| 不足の計算 | 集計 SQL（LLM 不使用） | $0 |
| 週次の目標補正 | 条件分岐（LLM 不使用） | $0 |
| 未知食品の栄養価 | `claude-haiku-4-5` | $1 / $5 |
| 買い物指示・週次レポート | `claude-sonnet-5` | $3 / $15 |
| 停滞の原因分析（必要時のみ） | `claude-opus-5` | $5 / $25 |

Hermes の API 呼び出しは 73% が固定オーバーヘッド（システムプロンプト＋ツールスキーマ）で、
エージェント用途は 64,000 トークン以上のコンテキストを要求する。
**節約の効き所はモデル選択ではなく、①LLM を使わない ②1コマンド＝1往復に固定する。**

想定コスト: 月 1,000〜3,000円。Anthropic Console で spend limit を先に設定する。

### スキーマ

**実体は `skills/health/db/schema.sql`。** ここに DDL を再掲しない
（同じスキーマを2箇所で管理するのは、この仕様書が REST API を却下した理由と同じ問題）。

設計上の要点だけ記す。

- **`meals` は栄養価を記録時点の値でスナップショットする。** `foods` を後から訂正しても
  過去の集計が黙って書き換わらないようにするため
- **`body.body_fat` は NULL 可、`source` 列を最初から持つ。** タニタ連携を後から足しても
  スキーマ変更が発生しない
- **`routines` は曜日ではなく `split`（push/pull/legs）で持つ。**
  実測1年分（`docs/training-history.md`）で曜日が固定されていないことが確認されたため。
  `t push` で番号付きメニューが出る
- **`targets` はテーブル。** 制御ループが毎週書き換えるので、いつ・なぜ変えたかを履歴で残す
- ビューを4つ持つ: `v_today`（今日の摂取合計）/ `v_target`（現在有効な目標）/
  `v_weight_weekly`（体重の週平均＝制御ループの入力）/ `v_1rm`（推定1RMの推移）

シードは `seed_exercises.sql`（種目39・ルーティン15・初期目標）と
`seed_foods.sql`（食品30品）。投入と検証は済んでいる。

**`sqlite3` CLI はこの環境に入っていない。** スキルは Python の `sqlite3` モジュール経由で
DB を触る（`apt install sqlite3` を前提にしない）。

### スキル分割

`skills/health/` に3つ。1スキル1動詞。統括スキルは作らない（3個の規模では不要）。

| スキル | 責務 | LLM |
|---|---|---|
| `log` | 記録。`m` `bp` `w` `t` のパースと投入 | 未知食品のみ Haiku |
| `today` | 今日の不足を出し、買うものを提案 | 集計は SQL、提案のみ Sonnet |
| `report` | `dashboard.html` 生成 + 週次の目標補正 | 不要（Sonnet は所見のみ） |

## 未決

- **`foods` の30品は全て `source='estimate'`（暫定値）。** 初回に買ったとき実物の栄養成分表示を
  見て `'label'` に更新する。その1回で正確になる
- 判読不明で未登録の種目2件 → `LATERAL LOW`（4/11, 4/18）と `シーテッド`（3/20）。
  次回ジムでマシン名を確認して `exercises` に追加する
- 現在の実摂取カロリー → 未測定。フェーズ1の7日で初めて分かる
- 有酸素（トレッドミル）を増量期に続けるか → フェーズ1の体重推移を見て判断

  Bluetooth のみだとスマホアプリを開かないとクラウドに上がらず、自動化にならない

## 却下

| 案 | 理由 |
|---|---|
| Anker / Eufy の体組成計 | 公式 API が無い。非公式実装は向こうのアプリ更新で黙って壊れる |
| Upstash / Vercel Postgres / Neon | アプリとデータが同じ機械にある。ネットワークを一周する意味がない。Postgres を選ぶと SQLite の身軽さが戻らない |
| REST API を立ててフロントから叩く | スキーマを2箇所で二重管理することになる。UI を盛る前に保守で力尽きる |
| IMD 食事分析 API | 法人向け商用。個人には非現実的 |
| 文科省 DB のみで商品名を解決 | 素材ベース。「サラダチキン」は載っていない |
| 毎回 LLM に栄養価を聞く | 毎回課金、商品改廃でズレる、ハルシネーションのリスク |
| Telegram をフェーズ1に入れる | 入力経路が増えると記録形式が経路ごとに散らばる。WSL2 では外部到達に VPS 移設が付随する |
| 能動通知を複数本 | 無視される習慣がつくとチャンネル全体が信用を失う |
| 筋トレ記録を自然言語で入力 | `bp 60 8,8,7` の方が速く、かつ無料 |
| ローカル LLM / GPU 購入 | 月 1,000〜3,000円の用途。60万円は回収に約7年、その前に GPU が陳腐化する |
| 「家をきれいにしたい」の並走 | 2つの目的を同時に走らせると両方止まる。同じ足場に後から足せる |
