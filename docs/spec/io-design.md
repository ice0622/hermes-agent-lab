# 入出力の設計 — Discord で完結させる

作成 2026-08-25 / 前提: `docs/spec/health-agent.md`, `docs/plan.md`

---

## 出発点: 今の実装で Hermes は何もしていない

事実を先に置く。

```
$ grep -rl "hermes" skills/health/     → 0件
$ find skills/health -name SKILL.md    → 0個
$ health CLI の依存                     → 標準ライブラリのみ（nl だけ anthropic SDK）
```

フェーズ0を「Hermes なし・LLM なし」で切り出した結果、**動くものができた時点で
Hermes の役割が消えていた**。これは設計ミスではなく、順序として正しかったが、
「では Hermes は何なのか」を決め直す必要がある。

## Hermes が実際に提供するもの

| 機能 | このプロジェクトで必要か |
|---|---|
| **ゲートウェイ**（Discord/Telegram/Slack/…20以上、送受信の両方） | **必要。** Discord で完結させるなら中核 |
| **cron / blueprint**（定時実行 + 任意の宛先に配信） | **必要。** 朝と夕方の配信 |
| **エージェントループ**（SKILL.md の散文を読んで手順を判断） | 曖昧な質問に答えるなら必要。定型入力には過剰 |
| **スキルが散文であること**（2つ目のドメインが markdown 1枚で足せる） | 「家をきれいにしたい」等を後で足すなら効く |
| セッションを越えた記憶 | **不要。** SQLite がその役割を担っている |
| 端末バックエンド（Docker/SSH/Modal…） | 不要 |

**「記憶」と「学習」は Hermes の売りだが、この用途では SQLite と診断ルールが
既にその具体形を担っている。** 残る価値はゲートウェイと cron、そして
「曖昧な入力を解釈して正しいコマンドに落とす」層。

---

## 3つの選択肢

### 案A — Hermes を使う

```
Discord ⇄ Hermes ゲートウェイ ⇄ エージェント ⇄ SKILL.md ⇄ health CLI ⇄ SQLite
                                    ↑ cron(blueprint)
```

- 書くもの: `SKILL.md` 3枚 + Hermes の設定
- **すべての Discord メッセージがエージェントの1ターンになる**（後述のコスト参照）
- 2つ目のドメインは markdown 1枚で足せる

### 案B — 素の Discord bot（Hermes を使わない）

```
Discord ⇄ discord.py bot ⇄ health CLI ⇄ SQLite
              ↑ systemd timer / cron       ↳ 自由入力だけ Haiku を1回呼ぶ
```

- 書くもの: bot 約200行 + cron 3本
- **定型入力（`w 64.2`）は API を呼ばない = 無料**
- 曖昧な質問（「来週の旅行中どうすればいい？」）には答えられない
- 2つ目のドメインは bot のコードを書き足すことになる

### 案C — 素の bot ＋ 逃げ道

素の bot で9割を処理し、解釈できないメッセージだけ LLM に渡す。
ただし「LLM に手順とツールを渡して判断させる」を自分で書き始めた時点で、
**それは Hermes の再実装**になる。案Cは案Bと案Aの間で必ず案Aに漂着する。

## コストの比較（実装後に改訂）

**当初の見積りは前提が間違っていた。** 実装して分かったこと:

`hermes cron create --no-agent --script <path>` は
**「LLM を完全にスキップして、スクリプトの stdout をそのまま配信」**する
（`--deliver discord` も標準対応）。つまり**出力側は全部トークン0円で作れる。**

実測で確認済み（`~/.hermes/cron/output/` に `Mode: no_agent (script)` で記録が残る）。

| | LLM を通るか | 月額 |
|---|---|---|
| **出力**（朝07:00 / 夕18:00 / 日曜21:00） | **通らない** | **$0** |
| 入力・定型（`w 64.2`） | 通らない（スキルが「解釈せず実行」を指示） | $0 |
| 入力・雑な記録（自由文） | Haiku 1回 | 約$0.0045/件 |
| 入力・曖昧な質問 | エージェント1ターン | 約$0.017〜$0.10/件 |

**コスト構造が「案A対案B」ではなく「入力の種類ごと」に変わった。**
案Aを選んでも、通知と定型入力は無料。課金されるのは自由文と質問だけ。

$41 のクレジットで、1日10メッセージ（うち自由入力3・質問1）なら
**おおよそ4ヶ月〜1年**。当初の「$41では0〜1ターン」は
トークン数と金額を読み違えた誤りだった。

> **未検証の前提**: Hermes が `cache_control` を設定するかは未確認。
> ただし通知と定型入力が無料になったので、影響範囲は「質問」だけに縮んだ。

## 判断

**案A（Hermes）を推す。** ただしコストの理由ではない。

1. **元の目的は健康管理ではなく「生活のアシスタント」だった。**
   「家をきれいにしたい」は却下ではなく保留にしてある。2つ目のドメインが来たとき、
   案Bは bot にコードを足す作業、案Aは markdown 1枚。ここで差が開く
2. **曖昧な質問に答えられるかどうかが、続くかどうかを分ける。**
   「今日何すればいい？」「あと何食べればいい？」は定型化できるが、
   「明日出張だけど何を買っておけばいい？」は定型化できない
3. **案Cは必ず案Aに漂着する。** 自分で書くと Hermes の再実装になる

**そして重要な点: どちらを選んでも `health` CLI は無駄にならない。**
Hermes スキルは散文であって、実処理はこの CLI を呼ぶだけ
（優勝作 Mom-n-Pop の `crm-lite` も同じ構造）。**CLI が資産、外側の層は差し替え可能。**
だからフェーズ0を先に作ったのは、この判断を後回しにできる形になっていた。

### 案Aの前提条件

- Hermes 本体の導入（未実施）
- Discord bot トークン
- **常時稼働ホスト。** WSL2 は常時稼働ではないので、PC を閉じると送信も受信も止まる。
  月700円程度のVPSが必要。推論は Claude API に投げるのでGPUは無関係、1GB で足りる

## 入力の設計

Discord に来るメッセージを3種類に分ける。**種類ごとに通る経路を変える**のがコスト設計の要。

| 種類 | 例 | 経路 | コスト |
|---|---|---|---|
| **1. 定型** | `w 64.2` / `bp 40 8,8,8` / `today` | CLI に直通。**エージェントを通さない** | $0 |
| **2. 雑な記録** | 「ベンチ40キロ8回3セット。昼はパン3つ」 | `health nl` 相当（Haiku 1回） | 小 |
| **3. 質問** | 「あと何食べればいい？」「明日出張だけど？」 | エージェント（Sonnet） | 大 |

**1をエージェントに通さないことが最大の節約。** Hermes のスキルには
「先頭が既知のコマンド形式なら、解釈せずそのまま実行する」と明記する。

### 入力の受け皿

- チャンネルは分けない。**1つのチャンネルに全部投げる**（分けると投げる前に迷う）
- 返信は必ず1行以上返す。**無反応が最悪**（入ったのか分からないと次から投げなくなる）
- 訂正は `undo`。打ち間違いを消せないと、記録が汚れるのが嫌で入力自体をやめる

## 出力の設計

Discord の制約: 1メッセージ2000文字、画像は添付可、埋め込み(embed)は整形が効く。
**HTMLダッシュボードは Discord にインライン表示できない。** 出力はテキストに寄せる。

| 時刻 | 内容 | 長さ |
|---|---|---|
| **07:00** | 今日のメニュー。今日の分割・種目と目標重量・食事の目安・体重測定の催促 | 15行程度 |
| **18:00** | 不足通知。「あと900kcal、タンパク質45g」＋買うものの具体名 | 5行程度 |
| **日曜21:00** | 週次レポート。体重の週平均と目標補正、停滞の指摘、次週の方針 | 20行程度 |

**通知は3本まで。** 増やすと無視される習慣がつき、チャンネル全体が信用を失う。

出力の書き方は `~/health/today.txt` で試した形を踏襲する（実使用でわかったこと）:

- **数値の羅列を避ける。** `47kg × 10,10,8` ではなく `47kg で 10回 → 10回 → 8回`
- **集計値をそのまま出さない。** `1431kcal / P121g` より「ぜんぶ食べれば目標に届く」
- 表を使わない（スマホで崩れる）。1行を短く保つ
- 時間順に並べる（朝 → 買い物 → ジム）
- **CLIコマンドを出力に混ぜない。** 打つのは別の場所

# 追記（2026-08-26）— Web ダッシュボードを見据えたときの層の割り当て

最終的に `dashboard.html` のようなものにスマホからアクセスしたい、という要件が出た。
そうなると「入力も出力も Web でいいのでは。Hermes は何のためにあるのか」という問いになる。

## Hermes の取り分を数える

インストールした Hermes は **142サブコマンド・63のゲートウェイモジュール**を持つ。
このプロジェクトで使っているのは **3つだけ**。

| 使っている | 用途 |
|---|---|
| `cron --no-agent` | 定時実行 + 配信（LLM 不使用） |
| `gateway` | Discord の送受信 |
| `skills` + エージェント | 曖昧な質問への応答 |

未使用: memory-graph / learning / kanban / moa / peer / computer-use / mcp / curator ほか多数。

## Web UI を作ると、その3つのうち2つが不要になる

| Hermes の機能 | Web UI があると | 代替の手間 |
|---|---|---|
| **定時実行 + 配信** | **不要になる** | **Discord Webhook に POST 1回 + systemd timer。約30行** |
| **Discord の受信（定型入力）** | **不要になる** | フォームの方が速い。パースもいらない |
| Discord の受信（雑な自由文） | 半分不要 | Web の textarea + Haiku 1回で同じ |
| **曖昧な質問への応答** | **不要にならない** | エージェントループを自分で書くことになる |

**残るのは1つ**。「明日出張だけど何を買っておけばいい？」のような、
定型化できない質問に答える層。

## それでも Hermes を残す理由は2つだけ

1. **push が本当に効くのはメッセージアプリだから。**
   Web ダッシュボードは *pull*（自分で開く）。開かなければ何も起きない。
   Web Push は Service Worker と VAPID 鍵と通知許可が必要で、iOS では特に不安定。
   Discord の通知は既に解決済みの経路で、追加コストがゼロ。
   → **朝7時に「今日は脚の日」が勝手に届く**のは Web では成立しにくい

2. **2つ目のドメインが markdown 1枚で足せる。**
   元の目的は健康管理ではなく生活のアシスタントだった。「家をきれいにしたい」は保留中。
   Web アプリで2つ目のドメインを足すのはコードを書く作業、Hermes なら SKILL.md 1枚。

**逆に言うと、健康管理だけで完結し、かつ曖昧な質問をしないなら、Hermes は不要。**
その判断は1ヶ月使ってから下せる（下記の逃げ道）。

## 層の割り当て（結論）

```
                    ┌──────────────────────────┐
                    │  SQLite（唯一の真実）      │
                    └────┬──────────┬──────────┘
                読み取り │          │ 書き込み
              ┌──────────┘          └──────────┐
     ┌────────┴────────┐            ┌──────────┴──────────┐
     │ Web ダッシュボード │            │ health CLI          │
     │ 見る・構造化入力   │            │ パーサー・集計・診断  │
     └─────────────────┘            └──────────┬──────────┘
                                                │
                              ┌─────────────────┴─────────────────┐
                              │ Discord（Hermes）                  │
                              │ push 通知 + 雑な入力 + 曖昧な質問    │
                              └───────────────────────────────────┘
```

| 層 | 担当 | 得意なこと |
|---|---|---|
| **SQLite** | 真実 | 変わらない。全部の層がここを見る |
| **health CLI** | 処理 | パース・集計・診断・HTML生成。LLM を使わない |
| **Web** | **見る**・構造化入力 | ダッシュボード、グラフ、フォーム。長さ制限なし |
| **Discord** | **push**・雑な入力・質問 | 通知が確実に届く。打つのが速い |

**Web と Discord は競合しない。** *pull* と *push* で役割が違う。
そして両方が同じ SQLite を見るので、片方を捨てても壊れない。

## 逃げ道（これがあるからこの判断は安全）

1ヶ月使って、**曖昧な質問を一度もしなかった** かつ **2つ目のドメインを足さなかった** 場合、
Hermes は次の置き換えで消せる。

```
Hermes cron --no-agent  →  systemd timer + curl で Discord Webhook に POST（約30行）
Hermes gateway          →  Web のフォームと textarea
Hermes agent            →  （そもそも使っていないので不要）
```

**SQLite と health CLI は一切変わらない。** だからこの選択に賭けの要素がない。
フェーズ0を先に作ったのは、この逃げ道を確保するためだった。

# 追記（2026-08-27）— 筋トレ入力のセッションモード

上の「入力の3分類」のうち **1. 定型** の設計を詰める。
2（雑な記録）と 3（質問）の経路は変えない。

## 問題は選択肢の多さではなく、文脈が無いこと

事実を先に置く。

```
種目コード  39個（実際に使うのは9個）
セット記法  2種類   bp 40 8,8,8  /  bp 40x8,37.5x8,35x6
番号指定    health 1 40 8,8,6  ← 先に `t push` を打った状態に暗黙依存
日付指定    無い
```

紛れるコードの実例: `sr`/`csr`、`sp`/`msp`、`lpr`/`slp`、`row`/`prow`/`ogr`/`iso`。
だから略記が使えず、コードを暗記する必要があった。

「ぶれる」の原因は書き方の選択肢ではなく、**毎回フル情報を書かされること**。
形式を増やすと悪化する。**文脈を持たせて省略を許す**方向にする。

## 決定

### 1. セッションを宣言し、名前解決の範囲を絞る

```
$ health start push

  push  （前回 8/19、8日空き）
    1. ベンチプレス            前回 37.5kg×8,7,8
    2. ショルダープレス（ダンベル）  前回 10kg×10,9,6
    3. サイドレイズ            前回 2kg×20,20,20
```

状態は `~/health/session.json`（`last_menu.json` と同じ置き場所）。以降:

| 入力 | 解釈 |
|---|---|
| `health 1 40 8,8,6` | メニュー1番 |
| `health ベンチ 40 8,8,6` | split 内の部分一致 |
| `health 1 8,8,6` | 重量省略 → 前回重量 |

**本質は「名前解決の探索範囲を split 内に限定する」こと。**
候補が39種目から3種目に落ちるので、「ベンチ」「ショルダー」「サイド」が一意に決まる。
コードを覚える必要が消える。

### 2. 重量省略は前回値を使い、必ず明示する

```
$ health 1 8,8,6
記録: ベンチプレス  37.5kg×8, 37.5kg×8, 37.5kg×6  （3セット）
  ! 重量省略 → 前回(8/19)の 37.5kg を使いました
```

黙って入れない理由が実測にある。**8/25 のレッグプレスは 30kg だったが、
7/7 の記録は 90kg。** 黙って前回値を使う設計なら、この日は 90kg が静かに入っていた。
警告を出せば `undo` できる。出さなければ気づけない。

セッション外（`start` していない状態）で重量を省略したらエラーにする。
文脈が無い場所での推測は事故になる。

### 3. セッションは日付が変わったら失効する

- `health end` は作らない。**明示的な終了は必ず忘れる**
- `session.json` に `date` を持ち、`date != today` なら無効として扱う
- 次の `health start <split>` で上書きする。
  同じ日に push と pull を分ける日は `start pull` を打てば切り替わる

### 4. 食事に定型を作らない

食事は**自由文 + 対話**（分類2の経路）に寄せる。`health m` は残すが推奨経路にしない。

理由: 品名と量の言い方が不規則で、定型にすると「書き方を思い出す」コストが
記録そのものより高くなる。実測でも、ユーザーの入力は「目玉焼き2個食べた」という
自由文で、`m 目玉焼き*2` への変換はエージェント側でやっている。
ユーザーに `*2` を思い出させる意味がない。

**この決定の副作用として `health <重量> <レップ>`（種目省略、メニューの上から順に埋める）が
使える。** 食事のフォールバックを取らないので、数字始まりの入力が食事と衝突しない。
ただし優先度は低い。番号1文字を打つのと打鍵差がほとんど無い。

## 前提として必要な追加: `--date`

食事を対話で入れる以上、**当日以外の記録が必ず発生する。**
8/25（筋トレ・体重・食事）と 8/26 で実際に起きた。
現状は日付を指定できず SQL 直叩きになり、`undo` が効かない状態で書き込んでいる。

```
health w 65.2 --date 8/25
health m --date 8/25 19:00 惣菜弁当
health start legs --date 8/25
```

`store.py` の 3関数（`write_train` / `write_body` / `write_meal`）が
`db.today_str()` / `db.now_str()` を内部で直接呼んでいるので、
呼び出し側から渡す形に変える。

## 実装順

1. **`--date` を3つの write に通す。** これが無いと対話入力が成立しない — **済（2026-08-27）**
2. `session.json` と `health start <split>` — 未
3. `resolve.resolve_exercise()` に split 引数を足し、探索範囲を絞る — 未
4. 重量省略 + `!` 警告 — 未
5. （任意）種目省略 — 未

```
■ 記録が続いていない  [要対応]
  直近7日の記録日数 3/7 日（目安は 4 日以上）
■ 体重の記録が足りず、目標カロリーを補正できない  [要対応]
  直近14日の体重記録 1 件（目安は 4 件以上）
```

**データが無い状態で入力形式を最適化しても、最適化の当たり判定ができない。**
セッションモード（実装順 2〜5）は保留し、自由入力を主経路にする。

## 実装したもの

### `lib/dates.py` — 日付表現の解決

**日付計算を LLM にやらせない。** モデルは表記を抜き出すだけ、解決は規則で行う。
「先週の火曜」の解釈が実行日でずれると、同じ入力が別の日付に入って記録が信用できなくなる。

| 入力 | 解決 |
|---|---|
| （書かれていない） | **今日**。`assumed=True` が立ち、出力で明示される |
| `8/25` `8-25` `8月25日` `25日` `2026-08-25` | その日付。全角も通る |
| `今日` `昨日` `おととい` `3日前` | 相対 |
| `火曜` | 直近の過去の火曜（今日が火曜なら今日） |
| `先週の火曜` | その7日前 |
| 年の無い `8/25` が未来になる場合 | **去年と読み、補正したことを警告する** |
| 読めない表記 | **今日として記録し、警告に回す**（記録を落とさない） |

### `nl` が食事・筋トレ・体重・日付をまとめて受ける

役割分担を明示的に切った。**モデルには抽出だけさせ、計算と解決はコードでやる。**

| 仕事 | 担当 |
|---|---|
| 品名・種目名・数量の抽出 | LLM |
| 日付の**表記の抽出** | LLM |
| 日付の**計算** | `dates.py`（規則） |
| 種目名 → 種目ID | `resolve.py`（DB） |
| 既知食品の栄養価 | `resolve.py`（DB） |
| 未知食品の栄養価の推定 | LLM（`foods` に `source='llm'` で追記） |

- **種目はマスタに無ければ記録せず `?` で報告する。** 食品と違って自動追加しない。
  分割（push/pull/legs）の割り当てが集計に効くので人が決める
- `nl.build_plan()` は API を呼ばないので、LLM の出力を固定すればテストできる

### `undo` が一括取り消しになった

1回の自由入力で食事・筋トレ・体重が同時に入る。最後の1件しか消せないと、
入れ直しが「undo を何回打つか」の当てものになる。
`last_insert.json` を `{"batch": [...]}` 形式にし、旧形式も読めるようにした。

## 残っている穴

- **`ANTHROPIC_API_KEY` が未設定なので `nl` はまだ動かない。**
  `.venv` に `anthropic` 1.0.0 は入っている。キーを入れれば通る
- **同じ日の体重を上書きしたあとの `undo` は上書き前の値を復元しない。**
  `body` は日付が UNIQUE で UPSERT しているため、元の値がどこにも残っていない
- `nl` が `foods` に追記した品は `undo` では消えない（記録だけ取り消される）
- プロンプトキャッシュは張っていない。`claude-haiku-4-5` の最小キャッシュ長は
  4096 トークンで、マスタ込みの prefix（約2.6Kトークン）はそこに届かない。
  **`io-design.md` 上部の「cache_control が効くか未検証」は、Haiku 4.5 では
  そもそも届かないという結論**（マスタが2倍に増えたら再検討する）

## この設計が変えないもの

- SQLite のスキーマ（`sets` / `meals` / `body`）は触らない
- 既存の `bp 40 8,8,8` 形式は動き続ける。セッションは**省略を許す追加**であって置き換えではない
- `nl` と診断・レポートの経路は無関係

# 追記（2026-08-27, 同日その2）— API を使えないので、LLM をブラウザに移す

`ANTHROPIC_API_KEY` が用意できないことが分かった。使えるのは
**ブラウザの Claude との会話**だけ。そのため `nl` は当面動かせない。

## これは制約ではなく、経路の入れ替えで済む

`nl` の設計では、役割分担をこう切っていた。

| 仕事 | 担当 |
|---|---|
| 品名・種目名・数量の抽出、日付の**表記の抽出** | LLM |
| 日付の**計算**、マスタ解決、書き込み | コード（`dates.py` / `resolve.py` / `store.py`） |

**この分担のうち LLM 側だけをブラウザに移せば、コード側は1行も変わらない。**
`nl` を作るときに「モデルには抽出だけさせる」と決めていたので、
LLM の呼び出し主体が誰かに依存していなかった。

```
【API 経路】   自由文 → health nl → API(Haiku) → dates/resolve/store → SQLite
【貼り付け経路】自由文 → ブラウザの Claude → 人が貼る → health batch → dates/resolve/store → SQLite
                                                        ↑ ここから先は同一
```

## 実装したもの

### `health prompt` — ブラウザに渡すプロンプトを出す

マスタ（食品・種目の全一覧）と書式の指示を1つの文字列にして標準出力に出す。約12KB。

```bash
health prompt > ~/health/master.md
```

**claude.ai の Project に添付すれば、毎回貼らなくて済む。**
マスタが増えたら出し直して差し替える。

マスタを渡さないと、ブラウザ側の Claude が品名を発明して
「マスタに無い品」として栄養価0で記録される。ここは省略できない。

### `health batch` — 返ってきたブロックをまとめて記録する

```bash
health batch <<'EOF'
food コンビニ豚焼き肉弁当 | 個 | 700 24 22 97 | dish | 豚焼肉弁当
ex   hip | ヒップスラスト | 臀部 | legs
--date 8/25 bp 40 8,8,6 --note 呼吸を意識する
--date 8/25 w 65.2
--date 8/25 m 08:00 おにぎり（鮭）*2, 納豆
EOF
```

**記録行の書式は既存の CLI とまったく同じ。** JSON のような新しい層を挟まなかった理由:

1. 人が貼る前に**読んで確認できる**。JSON は目で検算できない
2. 1行だけ手で直せる。全部やり直しにならない
3. パーサーを増やさない。`parse.py` がそのまま使える

新しい構文は `food` と `ex` の2つだけ。**これが今日いちばん必要だった穴埋め。**
マスタに無い品を入れるのに SQL を直叩きするしかなく、今日3品それでやって
`undo` が効かない書き込みを作ってしまっていた。

### 約束

- **1行が失敗しても止めない。** 通った行は記録し、失敗した行だけ行番号付きで報告して
  終了コード1を返す。1行のミスで全部やり直しになると、貼り直すのが面倒で記録をやめる
- **貼り付け1回 = `health undo` 1回。** どこまで戻したか分からなくなるのを避ける
- `food` は既にある品を**上書きしない**（実物のラベルで直した値を潰さない）

## 手数は1日2回のコピペ

1. ブラウザに自由文を書く
2. 返ってきたブロックを端末に貼る

**貼り付けは1回。** プロンプトで「端末にそのまま貼れる1ブロックだけを返す」と
指示しているので、`health batch <<'EOF'` から `EOF` まで丸ごとコピーできる。

## これが主経路でいいのか

**入力については、いい。** むしろ API 経路より優れている点がある。

| | API 経路（`nl`） | 貼り付け経路（`batch`） |
|---|---|---|
| 費用 | 1件あたり約 $0.0045 | **$0**（既存のサブスクリプション内） |
| モデル | Haiku（安さのため妥協していた） | **会話に使っているモデルそのまま** |
| 曖昧さの解消 | `?` を出して終わり。往復できない | **その場で聞き返せる** |
| 記録前の確認 | できない（実行と同時に入る） | **貼る前にブロックを読める** |
| 手数 | 1回打つだけ | **コピペ1回ぶん多い** |
| 常時稼働ホスト | 必要（Discord 経由なら） | **不要** |

**曖昧さをその場で往復できるのが一番大きい。** 「プロテイン」がどの製品か、
「おにぎり」の具が何かは、`nl` では `?` で報告して `undo` させるしかなかった。
会話ならその場で確定する。今日の会話が実際にそうなっていた。

### それでも Hermes / Discord が要るのは「出力」だけ

この文書の上半分で案A（Hermes）を推した根拠は3つあった。うち2つが弱くなる。

| 元の根拠 | 貼り付け経路が主だとどうなるか |
|---|---|
| 曖昧な質問に答えられる | **ブラウザで足りる。** むしろ会話のほうが自然 |
| 2つ目のドメインが markdown 1枚 | 保留のまま。ただし急がない |
| **push 通知**（朝7時に「今日は脚の日」が届く） | **残る。ブラウザは pull で、開かないと何も起きない** |

**残るのは push だけ。** そして push だけなら Hermes は要らない
（この文書の「逃げ道」に書いたとおり、systemd timer + Discord Webhook に POST で
30行程度）。

### 判断を保留する条件

**1ヶ月、貼り付け経路で記録を続けてから決める。** 判断材料は2つ:

- コピペ1回ぶんの手数で記録が続くか。続かないなら手数ではなく別の原因を疑う
- 朝の通知が無くて困るか。困るなら Webhook だけ先に作る（Hermes 全体は要らない）

**この判断が安全なのは、SQLite と `health` CLI が一切変わらないから。**
`nl` も残してあるので、キーが手に入ったら即座に切り替えられる。両方が同じ
`dates.py` / `resolve.py` / `store.py` を通るので、記録の中身は経路によって変わらない。

## セッションモードはどうなったか

実装順 2〜5（`health start push` / split 内での名前解決 / 重量省略）は
**引き続き保留。** 貼り付け経路では打鍵の最適化そのものが要らなくなる
（ブラウザに「ベンチ40キロ8回8回6回」と書くだけで、コードは Claude が書く）。

**定型で打つのは、ジムでその場で入れるときだけになる。** そのとき
セッションモードが効くかどうかは、貼り付け経路を1ヶ月使ってから判断する。
