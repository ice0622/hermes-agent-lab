# 実装計画

`docs/spec/health-agent.md` を実行順のタスクに落としたもの。

---

## 仕様からのフェーズ切り直し

仕様書のフェーズ1は「3つの Hermes スキル + マスタ投入」だった。**これを分割する。**

理由。フェーズ1の中身を並べると、**LLM が必要なのは2箇所だけ**だと分かる。

| やること | LLM が必要か |
|---|---|
| 筋トレ・体重・既知食品の記録（パーサー） | 不要 |
| 今日の不足の計算 | 不要（SQL） |
| 週次の目標補正 | 不要（条件分岐） |
| ダッシュボード生成 | 不要 |
| 1年分の過去データ投入 | 不要 |
| **未知食品の栄養価を引く** | **必要**（Haiku） |
| **買い物指示・週次の所見** | **必要**（Sonnet） |

つまり**記録を始めるのに Hermes も API キーも要らない**。Hermes 本体はまだ未インストールで、
導入 → プロバイダ設定 → スキル探索の確認、で詰まると**その間ずっと記録が始まらない**。
1年続いている習慣を置き換える仕組みなのに、着手が数日遅れるのは筋が悪い。

そして Hermes スキルは散文であって、実処理は結局 Python スクリプトを呼ぶ
（`crm-lite` も同じ構造）。**スクリプトは先に要る。**

→ **フェーズ0（Hermes なし・LLM なし）を切り出し、明日から記録を始める。**
Hermes はその上に後からかぶせる。

### T02 パーサー — フェーズ0で一番重要

入力の摩擦がここで決まる。仕様通り、**LLM を通さない**。

```
bp 60 8,8,7        → sets に3行（ベンチプレス 60kg × 8/8/7）
bp 60 8 60 8 55 7  → 重量が変わる場合の別記法
w 64.2             → body に1行
m サラダチキン, おにぎり*2, 味噌汁   → meals に3行（カンマ分割 + `*n` で個数）
t push             → push のメニューを番号付きで表示
1 60 8,8,7         → t の直後なら番号で種目を指定
```

- 種目は `code`（`bp`）と `alias` の両方で引く
- 食品は `name` と `alias`（`サラチキ` → `サラダチキン`）で引く
- **マスタに無い食品が来たら、エラーにせず「未知」として保留し、記録自体は通す**
  （記録が止まるのが最悪。栄養価はフェーズ1で Haiku が埋める）

### T06 過去データ投入 — 効果が大きいので先にやる

`docs/training-history.md` は既に構造化されている。**これを `sets` / `body` に流し込むと、
初日からダッシュボードに1年分のグラフが出る。**

空のダッシュボードは続かない。初日に「体重が −3.5kg 落ちている」「ベンチが8ヶ月止まっている」
が目に見える状態から始まるのは、モチベーション上の差が大きい。しかも**データは既に手元にあり、
コストはゼロ**。

- 判読不明の `(?)` 付きは投入するが `note` に原文を残す
- 未登録の2種目（`LATERAL LOW` / `シーテッド`）はスキップしてログに出す
- 冪等にする（何度流しても重複しない）

### T07 ダッシュボード — 白黒モノクロ、SVG 直書き

`dashboard.html` を1ファイル書き出す。JS ライブラリも CDN も使わない。

載せるもの（優先順）:

1. **体重の推移**（日次の点 + 週平均の線）← 制御ループの入力そのもの
2. **今日の摂取 vs 目標**（kcal / P / F / C の4本のバー）
3. **ベンチ・スクワット・デッドリフトの推定1RM推移**
4. 週あたりのトレーニング頻度
5. タンパク質の供給源トップ5（`meals` を品目単位にした見返り）

### T11 は飛ばさない

Hermes は1ターンで複数回モデルを呼ぶ。ドキュメント自身が「無料枠のキーは数ターンで枯れる」と
警告している。**先に上限を設定する。**

### T15 が本命の機能

「あと 900kcal、タンパク質 45g 足りない」に対して、`foods` マスタから実際に買える組み合わせを
出す。すでに検証済みの例:

- おにぎり（鮭）×2 + プロテイン + ナッツ = 635kcal / P39.0
- 牛丼（並）1杯 = 635kcal / P20.0（最も手数が少ない）

**モデルに毎回0から考えさせない。** マスタから組み合わせを SQL で作り、
Sonnet には「どれを勧めるか」だけ選ばせる。これで呼び出しが短くなる。

## 検証と撤退条件

仕様書に撤退条件が無かったので足す。**目標ではなく、手段の撤退条件**。

| 何を | いつ | 満たさなければ |
|---|---|---|
| CLI で7日連続の記録 | **2026-09-07 まで** | 入力形式が間違っている。CLI をやめて別経路（Telegram / 音声）を検討 |
| ダッシュボードを週1回以上開く | 2026-09-30 まで | 見ていないものを作っている。静的HTMLをやめて通知だけにする |
| 週平均体重が上向く | 2026-10-31 まで | 目標カロリーの推定か、記録の正確さが間違っている |
| 紙をやめる | CLI 入力が3週間続いた後 | それまでは紙を捨てない |

**「体重が増えない」は撤退条件ではない。** 制御ループが目標値を上げるので、
それが機能しているかを見る。機能していないなら記録が不正確（＝ `foods` が
`estimate` のまま）ということになる。
